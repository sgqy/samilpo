# Samilpo SMC 文件格式逆向研究：第三阶段
## SMC 二进制格式规范的深入恢复

### 一、项目目标

通过 REA MCP、Ghidra、现有 SMC 样本和必要的本地分析工具，继续恢复 Samilpo 2.0 使用的 `.smc` 乐谱文件格式。

最终目标是建立一份尽可能完整、精确、可验证的 SMC 文件格式规范，使没有原始软件和源代码的第三方开发者，也能够依据文档理解、解析并解释 SMC 文件。

**本阶段专注于格式逆向与规范编写，不开发格式转换器。**

特别要求：

- 不设计 IR。
- 不研究 MusicXML 或其他目标乐谱格式。
- 不编写 MIDI、XML 或其他格式的导出程序。
- 不以能否转换为某种现有格式作为字段研究的优先级标准。
- 不要求一次研究结束后消除所有未知字段。

当前研究任务是弄清 SMC 文件本身，而不是研究如何迁移数据。

### 二、研究环境

目标程序：

- `C:\Program Files (x86)\Samilpo 2.0\MusicBook.exe`
- `C:\Program Files (x86)\Samilpo 2.0\engine.dll`

参考代码：

- `C:\MSVC600-master`

使用：

- 已连接的 REA MCP。

- 现有 SMC 样本集合。
- workspace 中已有的 Python 分析工具。

#### Python 环境

允许在 workspace 中创建独立的 Python 虚拟环境 `.venv`，并使用 pip 安装研究所需的第三方库，例如 `fonttools`。

要求：

1. 优先复用现有 Python 工具。
2. 仅在有具体分析需要时引入依赖。
3. 记录安装的依赖和版本。
4. 将 `.venv` 排除在版本管理和研究成果归档之外。
5. 不修改系统 Python 环境。
6. 不执行来源不明的安装脚本。

允许编写实验性解析、提取、统计和验证脚本，但不开发完整转换程序。

### 四、研究任务 A：全面整理 SMC 格式规范

首先整理已有 `docs/smc-format.md`，明确目前已经恢复的结构。

按照文件实际结构组织规范，而不是按照 Ghidra 调查顺序组织。

至少包括：

1. 文件标识、版本和基本头部。
2. 整体文件布局。
3. 字节序、数据类型、长度字段和对齐规则。
4. 对象记录格式及其嵌套关系。
5. 对象 key 和跨对象引用。
6. System、Staff、Meas、Msg、Page、Block 等结构。
7. 不同 Msg type 的记录布局。
8. 字符编码、字符串存储和文本关联。
9. 资源、字体、图片及未知扩展区域。
10. 版本差异、异常结构与兼容性问题。

对于每个已识别结构，尽可能给出字段级描述：

| Offset | Size | Type | Meaning | Evidence |
|---|---|---|---|---|

表格使用相对于当前结构起点的偏移。

需要明确：

- 固定长度与可变长度字段。
- 数值类型和字节序。
- 指针、文件偏移、索引与对象 key 的区别。
- 字段的有效范围和特殊值。
- 记录长度与嵌套边界的计算规则。
- 不同版本中字段含义是否变化。
- 未知字节是否可以被原样保留。

禁止把内存对象布局直接当成磁盘结构，除非有明确证据证明两者一致。

### 五、研究任务 B：扩展消息类型与字段覆盖

这是本阶段的主要逆向任务。

对当前已发现但尚未完整解释的 Msg type 进行分类，优先调查样本中出现频率较高、对文件结构具有明显影响的类型。

重点覆盖：

- 普通音符及休止符。
- 音高和音符属性。
- 时值、附点、连音及节拍相关字段。
- 和弦与音符组。
- 拍号、调号、谱号和变音记号。
- 小节线、反复记号及其他演奏控制。
- 音符间连接、连线和装饰符号。
- 文字、歌词、标题和注释。
- 页面、谱表、系统与对象布局。
- 图片及其他嵌入资源。

这些类别只是研究方向，不代表 SMC 必然以相同方式组织数据。

研究时应从已有消息类型索引出发，利用 REA 查找对应的 Read、Write、Draw、Edit、播放或其他消费者函数。

对每一种 Msg type，尽可能确认：

1. 对应的程序类或处理函数。
2. 序列化 head 的字段划分。
3. ObjectCore 与其他公共字段的作用。
4. 字段的读取和写入方式。
5. 字段如何参与实际行为。
6. 与其他对象的引用关系。
7. 在真实 SMC 文件中的取值分布。
8. 是否存在版本相关变化。

优先取得实际证据，不仅凭类别名称猜测数据布局。

### 六、研究任务 C：字体、字形及特殊编码

在前两阶段韩文解码研究的基础上，进一步调查字体与记谱字形。

允许使用 Python venv 和 fonttools 等工具。

重点研究：

- 原软件引用哪些字体。
- 字体文件与 `.cod` 码表之间是否存在关系。
- 韩文文本和音乐符号是否使用不同的字符映射。
- 是否存在专用音乐字形、私有字符或自定义编码。
- 乐谱符号使用什么字形索引或绘制机制。
- 文件中是否存储字体名称、字号、字形编号或样式属性。
- 是否存在仅能通过特定字体正确解释的字段。
- 字体资源是否包含与 SMC 文件语义恢复直接相关的信息。

如果实际符号由矢量绘制、位图资源或 Windows GDI 指令产生，不应强行解释成字体字符。

分析字体的目标是理解 SMC 文件中的字段，而不是制作替代字体或移植渲染系统。

允许创建字形索引、字符映射表与必要的本地分析结果。

### 七、研究任务 D：其他资源与特殊结构

在主要 Msg 类型取得进展后，继续调查：

- 图片资源与文件内存储形式。
- 分页信息与页面布局。
- 额外文本、标题和注释。
- 不同版本的兼容路径。
- 文件内部可能存在的压缩、校验或特殊编码。
- 未知数据块及扩展记录。

优先研究具有真实样本的结构。

遇到少见类型时，应记录出现数量、典型样本和处理函数。若需要大量额外调查才能确认，可以保留为后续问题，不必本阶段全部解决。

### 八、实验与验证方法

鼓励使用以下研究循环：

1. 根据现有规范确定未知字段或结构。
2. 在 Ghidra 中定位读取、写入或消费该字段的函数。
3. 提出具体、可以证伪的字段含义假设。
4. 编写必要的 Python 实验脚本。
5. 利用真实 SMC 样本进行验证。
6. 对不成立的假设记录反例。
7. 将确认结果写入格式规范。
8. 更新剩余未知项与下一步调查方向。

不需要为了每个小假设创建一个永久脚本。允许保留探索性 `_probe_*.py`，但应在任务完成后归档、标明用途或整理已经验证的逻辑。

全量样本扫描应针对明确的验证问题，而不是反复无差别地遍历所有文件。

对于字段语义，应区分：

- **Confirmed**：有明确读写或使用代码支持，并经过适当验证。
- **Inferred**：证据较强，但尚未充分证明。
- **Unknown**：尚无可靠解释。
- **Contradicted**：曾提出但被证据推翻的假设。

不允许将统计相关性直接写成已经确认的格式规则。

## 二、执行步骤

### 步骤 1 — 从函数索引进入，定位消息读写路径
- 搜索 `MidiKey` / `PlayTime` / `WholeCount` / `DrawMsg` / `Msg::` / `CSMObject::` / `Midi` 等，
  避免全程序无目标搜索。
- 关键发现：`CSMMsg::Read` 0x1007a490 与 `CSMMsg::Write` 0x1007a240 **互为逆操作**，
  据此得到 MsgHdr 的**磁盘布局**（而非内存布局），满足任务书「禁止把内存对象布局当磁盘结构」的要求。

### 步骤 2 — 消息头与对象头
- 反编译 `CSMMsg::Write`/`Read` → 0x2C 消息头 24 个字段逐一对应（`project/phase3-log.md` §1.1）。
- 反编译 `CSMObject::Write`/`Read` → ObjectCore 12 字节头；发现 **`+06 = headLen + 12`**，
  且 `+01` 为写入未初始化栈的保留字节（读取端忽略）。
- 反编译 `CSMObject::AddMsg`/`InsertMsg`/`Write` → Child 8 字节 = `u32 key, u8 role, u8 pad[3]`。

### 步骤 3 — 音符语义
- `GetMidiKey`/`SetMidiKey` → **head[0] = MIDI key**。
- `GetVelocity`/`SetVelocity` → **head[1] = velocity**。
- `GetRealNoteDur` → **head[4..7] = u32 时值**；`SetPlayTime` 回写同字段。
- `UpdateStartTime` → **head[8..11] = 起始时间**（磁盘恒 0）。
- `MakeMidiMsgFromY` → head 默认值 100 / 0x40 / 0，与语料 head[2]=0x40 一致。
- `CalcPlayTime` → `+0x5E` 为时值指数；`+0x77` 为附点；`f2` 为连音比例。

### 步骤 4 — 类型分派全表
- 反编译 `CScoreView::SMDrawMsg` 0x1004aa00 → **唯一按 type 分派的 switch**，覆盖 0x01–0x4A。
- 用 `search_procedures "CScoreView::Draw"` 建立绘制器地址表（69 个）。
- 用 `find_xrefs_to_name` 定位符号常量（`codeDot`/`codeStdHead`/`CodeDyn`/`codeAcci`）。

### 步骤 5 — 结构与布局
- `CSMMeas::Read`/`CalcWholeCount` → 拍号分子/分母、小节 tick、9 声部。
- `CSMStaff::Read` → 0x70 尾块字段表。
- `CSMSystem::Read` → nStaff1/nStaff2/wholeTick、连音键重映射。
- `CSMPage::Read` + `CSMBlock::Read`/`Write` → 页面与排版块（Write 的 `_Size` 与 Read 完全吻合）。

### 步骤 6 — 全语料验证（Python）
- `tools/smc_census.py`：**8451/8451 文件精确消耗主体、尾部恰好 4 字节**。
- `tools/_probe_p3_fields.py`：ObjectCore `+06 - headLen = 12`（68610/68610）；key/velocity ≤127；
  时值样本；附点 {0,1,2}；拍号分布。
- `tools/_probe_p3_heads.py` / `tools/_probe_p3_heads2.py` / `tools/_probe_p3_note.py`：head 前 4 字节与
  head[8..12] 的取值分布。
- 结论：**统计只用于验证已由代码支持的结论**，未把相关性写成规则。

### 步骤 7 — 字体与符号
- `tools/_probe_font_cmap.py`（纯 Python 解析 cmap，未安装第三方库）：
  `KAYAKUMA.TTF` 的 cmap **仅覆盖 U+F020–U+F0FF**；`wkgothic.ttf` 对 889F→Unicode 覆盖率 98.7%。
- `tools/_probe_kayakuma.py`：字体名 "KayakumA"，223 字形，`post` 2.0。
- `tools/_probe_symbols.py`：889F 正向表**没有**码位映射到 U+F000–U+F0FF；
  引擎符号常量表位于 `0x10100380` 起。
- 结论：**音乐符号与韩文文本使用互不重叠的两套编码空间**。
