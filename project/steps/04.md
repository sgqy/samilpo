# Samilpo SMC 文件格式逆向研究：第四阶段
## 未知字段收敛、特殊结构恢复与动态分析准备

### 一、总目标

继续逆向恢复 Samilpo 2.0 所使用的 SMC 二进制乐谱格式。

项目终极目标是尽可能解释 SMC 文件中每个字节的结构、数据类型、取值规则与语义，并形成可由第三方独立使用的完整格式规范。

本阶段集中解决第三阶段留下的未知字段、特殊消息类型以及部分文件级结构，并评估引入动态调试的必要性与可行性。

**本阶段仍然是格式研究，不实现转换器，不设计 IR，不研究 MusicXML。**

允许编写实验性解析、字段提取、字节对照和验证脚本。

不要求一次完成所有未知字段，但必须系统记录覆盖范围、证据和剩余问题。

### 四、任务 A：完成低成本静态分析收尾

优先解决已经有明确函数入口的未知字段。

#### A1. 歌词 head 的未解释字节

重点：

- `CSMLyricMsg::DrawMsg` 0x1009ad00
- `CTempLyricMsg` 0x100c9b70
- `BeginDrag` 0x100c9cf0

首先恢复 head +0x02/+0x04 的精确字段归属。

必要时检查原始汇编与栈变量偏移，不仅依赖 Ghidra 伪代码的局部变量类型。

随后调查 +0x06/+0x0D/+0x0E/+0x0F 是否具有独立语义。

若静态证据不足，记录适合动态验证的断点位置和具体操作，不应反复猜测。

#### A2. 文件尾部字段

检查 `CSMDoc::Save` 0x100773c0。

确认文件尾 4 字节的写入规则及其与 bodyLen 的关系。

#### A3. 符号常量表

完成现有音乐符号常量表的导出与整理。

只读取必要的静态数据段，避免重新分析整个字体体系。

### 五、任务 B：特殊消息结构恢复

按实际样本覆盖与研究收益排序，优先处理：

1. type 0x45：headLen 100 的特殊缓存结构。
2. type 0x46：`CFretInfo` 指板数据。
3. type 0x47：`CRtmData` 节奏数据。
4. type 0x2C：长休止符。
5. type 0x0C：Coda。

已知线索包括：

- `CFretInfo::ReadFromMem` 0x1002dc70
- `CRtmData::ReadFromMem` 0x10047720
- `CRtmData::GetRealMidiKey` 0x10047410
- `DrawLongrest` 0x100595b0
- `DrawCoda` 0x10056ec0
- `DrawCodaEx` 0x10065660

以 `project/function-index.md` 为准复核模块与地址。

重点：

- 恢复 head 内每个字段的偏移及宽度。
- 找到初始化、读取、写入和消费字段的代码。
- 区分持久化数据、派生数据及运行时缓存。
- 对复杂结构建立精确的二进制布局表。
- 利用真实样本验证字段解释。
- 查明相关子对象引用关系。
- 判断是否存在可变长度部分或版本差异。

对于 type 0x45 的 100 字节数据，特别调查哪些字节来自实际文件语义，哪些属于运行时生成的缓存内容。

对于无法确定的内存指针、填充区域和缓存值，应明确说明读取方如何处理，而不是试图赋予它们不存在的音乐语义。

### 六、任务 C：文件级与布局结构的剩余字段

继续研究：

- SYMP 文件头未知字段。
- SMC 固定块的未解释部分。
- `CSMCtrlTool` 的剩余字段。
- `CSMFileInfo` 的剩余字段。
- Meas 尾块中的未知字段。
- 文件偏移 0x590 附近的附加字符串。

优先函数：

- `CSMFileInfo::SetLogicPageInfo` 0x10094ed0
- `CSMFileInfo::UpdateLogicDoc` 0x100950a0

沿着字段消费者、默认值设置和保存路径分析。

对于只在 GUI 初始化、绘制或打印过程中使用的字段，允许暂时记录为需要动态验证。

如果发现与页面排版、打印、字体缩放或编辑器窗口状态有关，应明确区分文档持久属性与程序运行状态。

### 七、任务 D：动态调试可行性调查

这是独立的预备任务，不应阻断 A、B、C 的静态研究。

目标是判断现有 Windows 环境能否提供可由 Agent 调用的动态分析接口，以帮助解决静态分析无法明确的字段。

#### D1. 调查调试器接口

检查当前环境中是否已安装：

- x32dbg / x64dbg
- WinDbg
- Ghidra Debugger
- 其他已有调试工具

调查是否存在适合当前环境的维护中 MCP 调试桥接方案，或者可通过稳定脚本接口控制的调试器。

不得因为名称包含 MCP 就认定工具具有完整的调试功能。

评估时确认：

- Windows x86 程序支持情况。
- 是否支持启动或附加目标进程。
- 是否能设置软件断点、继续执行与单步运行。
- 是否能读取寄存器和内存。
- 是否能获得模块基址及 ASLR 重定位后的函数地址。
- 是否能够导出结构化调试结果。
- 是否支持与 OpenCode 集成。
- 是否需要管理员权限或额外驱动。
- 是否具有活跃维护和可审核的源代码。

优先考虑能够复用现有工具的最简单方案。

不要求自行开发完整调试器 MCP Server。

#### D2. 动态实验最小闭环

如发现可用方案，制定一次最小实验：

1. 在隔离环境启动 MusicBook.exe。
2. 对已知的 SMC 文件读取函数设置断点。
3. 由用户手动打开一个已知 SMC 文件。
4. 在断点处读取必要的寄存器与内存。
5. 将运行时数据与静态结构文档对应。
6. 保存调试记录与程序版本、文件哈希。
7. 关闭实验。

优先验证已知结论，而不是直接攻击最复杂的未知字段。

不得在未经用户确认的情况下启动目标程序、修改环境、安装调试驱动或执行自动化 GUI 操作。

#### D3. Windows 消息与 GUI 操作

调查 MFC 的消息路由：

- WM_COMMAND
- 控件通知
- 文档与视图命令处理
- 文件打开及编辑命令的实际调用路径

可以静态识别候选命令 ID、处理函数和消息映射。

但不要求本阶段自动发送 Windows 消息。

需要说明：

- 哪些操作可以由人工触发。
- 哪些操作适合使用 SendMessage/PostMessage。
- 哪些操作需要真实输入事件或内部对象状态。
- 哪些操作可能涉及模态对话框。
- 哪些操作适合后续自动化。

不要假设发送 WM_COMMAND 就等价于用户完成一次真实编辑操作。

#### D4. 动态调试交付物

形成 `project/debugging-plan.md`，说明：

- 推荐的技术组合。
- 当前环境能否实现。
- 安装与配置前提。
- 最小验证实验。
- 已知技术限制。
- 需要用户执行的操作。
- 计划验证的 SMC 未知字段。
- 是否值得在后续阶段实际实施。

如果没有可靠方案，只记录可行路径和障碍，不要无限尝试安装各种 MCP 项目。

### 八、任务 E：完善格式规范的覆盖度

在现有文档基础上增加一个字段覆盖清单。

至少区分：

- 已确认含义。
- 已确认读写规则，但语义未明。
- 已确认无语义的填充、保留或未初始化数据。
- 仍存在多个可能解释的字段。
- 完全未知的区域。
- 当前样本未覆盖的条件分支。

针对每个结构，记录：

- 总长度。
- 已解释字节范围。
- 未解释字节范围。
- 具体证据。
- 适用版本。
- 是否已经过样本验证。
- 推荐的后续验证方式。

覆盖度统计必须保持口径一致。

不能简单将未知保留字节计为错误，也不能把已确定长度但未确定语义的整个结构计为完全已解析。

可为每个结构分别计算结构覆盖率与语义覆盖率。

最终目标不是获得好看的百分比，而是使每个未知范围都具有明确的位置和研究状态。

## 二、执行步骤

### 步骤 1 — A1：歌词 head 的字节归属（**闭合**）

- 反编译 `CSMLyricMsg::DrawMsg` 0x1009AD00，**并读其原始汇编**（不依赖 Ghidra 局部变量类型）。
  据 `memcpy(&local, head, 0x10)` 的栈偏移（`EBP-0x20` 起）逐一确定字段归属：
  `+0x00 u16 字体 / +0x02 u8 样式 / +0x04 u16 字号 / +0x08 u32 颜色 / +0x0C u8 文本长度`。
- 反编译并读 `CSMDoc::EncToSMC_Lyric` 0x10025170 的原始汇编：head 缓冲基址 `EBP-0xC8`，
  仅写同样的 5 个字段；**未写** `+0x03/+0x06/+0x07/+0x0D/+0x0E/+0x0F`。
- 与 `CSMDoc::GulsamToSMC_Lyrics` 0x10030010 的 `memcpy(...,&local_ac,0x10)` 交叉验证。
- 结论：读取侧未访问集合与写入侧未写入集合**完全一致** → 6 个字节为未初始化栈残留。
- 验证：新增 `tools/_probe_p4_lyrichead.py`，400 文件 / 30353 条记录 →
  样式 {0: 30254, 1: 99}、字号 {13: 30136, 14: 140, 12: 74, 0: 3}、
  `+0x06` 有 317 个不同值、`+0x0D..+0x0F` 有 535 种组合（仅 6089 条全 0）→ 预测成立。

### 步骤 2 — A2：文件尾 4 字节（**闭合**）

- 反编译 `CSMDoc::Save` 0x100773C0：起始处写占位 → 写 System → 写主体并累计 → 尾部写同一累计值
  → 回到起始处回填 → 回到尾部之后。
- 结论：尾部 4 字节为 **bodyLen 的冗余副本**，由 writer 主动写入；与阶段一「全部样本相等」一致。

### 步骤 3 — A3：符号常量表导出

- 用 `find_xrefs_to_name` 定位 `codeDot` / `codeStdHead` / `codeDyn` / `codeAcci` /
  `codeSmallDigit` / `codeSlid` / `codeShortLine` / `codeSlashHead` / `codeBoxHead` /
  `codeCrossHead` / `codePedal` / `codeMeasRepeat` 的地址。
- 用 `read_bytes` 导出 `0x10100360`–`0x10100700` 区段，整理为 12 个常量表（见 `docs/font-resources.md` §4.2）。

### 步骤 4 — B1：type 0x45 的 headLen 100（**性质确定**）

- 新增 `tools/_probe_p4_rhythm.py`：全语料 413 个 0x45 带 100 字节 head。
- 关键发现：head 内含 **`Ptr32`（0x5F401018 / 0x5F40111F / 0x5F405D25，落于 MFC42.DLL 段）**
  与栈值（`0xBFF7`）；100 字节中仅 27 字节在全部样本恒定。
- 结论：**持久化运行期结构，无语义，须原样保留**。

### 步骤 5 — B2/B3：type 0x46 指板与 0x47 节奏（**结构级恢复**）

- `CFretInfo::ReadFromMem` 0x1002DC70 与 `WriteToMem` 0x1002DD00 逐字节对照 → 16 字节三段布局；
  再用 `GetMidiKeyOfString` 0x1002D220、`FretInfoToLineString` 0x1002D330、`IsFretEmpty` 0x1002D2A0
  确定为「基准品位 / 6 弦品位 / 4 组端点对」。
- `CRtmData::ReadFromMem` 0x10047720 与 `WriteToMem` 0x10047950 逐字段对照 → 顶层结构；
  探针验证 `totalSize = 已消耗 + 4`（101/101）、`stride = 16`、`eventSize = 16`、`size2 = 6`。
- 事件体与第二段内部字段**未解析**，记入 `docs/unknown-fields.md` B4。

### 步骤 6 — B4：type 0x2C 长休止

- 反编译 `DrawLongrest` 0x100595B0：发现中间打印的十进制数字取自 **`MsgHdr+0x1C`**（非 head）。
- head 60 字节未解析（B2）。

### 步骤 7 — D1：动态调试可行性（**只读勘察，未安装**）

- 勘察本机：发现 **x64dbg/x96dbg（含 x32 headless.exe）**、**IDA Pro 9.5（含 idalib）**、**Cutter 2.4.1**、
  Ghidra 项目 `samilpo.gpr`；未发现 WinDbg / Frida。
- 实测 x32 `headless.exe`：进入命令循环、接受 stdin 命令、`quit` 正常退出、支持日志重定向。

- 交付 `project/debugging-plan.md`：推荐 x64dbg x32 headless；最小闭环设计；**未执行**，需用户确认。
